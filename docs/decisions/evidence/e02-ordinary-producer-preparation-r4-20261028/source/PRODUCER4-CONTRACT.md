`guard-client-core.mjs` serializes short synchronous continuations. The one
in-flight request and all queued entries share a64-entry/16MiB bound. A reply
binds exact instance/run/lease/sequence/label/context/request bytes and is consumed

epoch/fault is checked again after a synchronous effect, so an effect that
cancels its owner cannot retain a success row. Timers and socket/helper/capture
faults fence outside the queue. Cleanup cannot erase the first fault.

Production UTC/BOOT observations are conservative intervals: Date.now has a1ms
quantum; /proc/uptime exposes an explicit decimal quantum (usually10ms).
MONOTONIC samples bracket this bounded proc read. Enqueue uses lower bounds,
consume uses upper bounds, so adding5s to a rounded enqueue upper bound cannot
extend the decision. UTC/BOOT/MONO enqueue deadlines all apply; a held response
across suspend cannot survive by relying on a paused MONOTONIC timer. Exact
original Python clock samples stay decimal strings in the raw reply. This is
cooperative Linux timing under the original host/time-namespace assumptions,
with conservative early refusal; it is not atomic multi-clock or crossprocess
revocation attestation. This interval strategy still requires independent
SOURCE assessment and actual suspend/clock adversary evidence before release.
